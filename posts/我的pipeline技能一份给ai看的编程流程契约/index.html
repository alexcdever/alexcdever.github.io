我的 pipeline 技能：一份给 AI 看的编程流程契约

pipeline 是我写的一份纯流程契约：不绑定任何具体的 agent 软件——它规定主代理、执行子代理、审查子代理在做编程任务时怎么协作，什么算完成、什么不算。没有脚本、没有工具、没有运行时，只有一份 SKILL.md 契约、一份术语表、一份残留恢复手册。仓库在 GitHub：alexcdever/pipeline。

写它的起因很朴素：单次大模型调用写代码，要么上下文爆了，要么写完没人验，要么改完把别处弄坏了没人发现。我想要的不是「让 AI 写代码更快」，而是「让 AI 写代码更有效率」——更重要的是降低我自己的决策成本：能自己判断的自己判断，能自己收拾的自己收拾，人只在真正需要裁决的地方出现。

核心结构：三个人 + 一个 worktree

这套流程的开销按任务计，不按改动大小计。每个任务的最小开销是：预走一遍验收标准、派执行者与审查者各一个独立子代理、建一个 Git worktree、留四个文件、跑一次合并后复验，外加三次全量测试——改动只有三行，这七步也一步不能省。

  • 主代理：面向用户，决定做什么、什么算完成。规划、写任务描述、派发、核对、合并。自己不改产品代码。
  • 执行子代理：在隔离 worktree 里实现，遵循测试驱动——先红、最小实现、重构。
  • 审查子代理：在独立上下文里亲手复验，不采信任何转述，只看代码、测试和自己跑出来的结果——包括自己再跑一次全量测试。

三个角色绕着一个 worktree 走七步：摸底 → 建 worktree → 写任务描述 → 派执行 → 派审查 → 合并 → 清场。中间每一步都有明确的「什么算证据」——退出码为 0 不算验收，必须检查实际状态变化；task.md 里写的范围是白名单，不在里面的改动算越界；审查者先写自己的结论，再读执行者留下的东西对照。

几个踩过坑后写下的规则

这份契约里大部分条款都是踩过一次坑之后才加上的。挑四条：

子代理说「做完了」，不代表活真的干完了

有一次执行者回报完成，实际上一个提交都没有——它的上下文全花在翻代码、找文件上了。这种回报既不算「执行失败」，也不能直接送去审查：审查者只能对着一份空 diff 白跑一轮。正确的做法是就地重派，但必须把这一轮它已经探明的事实（数据在哪、函数叫什么、口径怎么定）一并写进新的派发材料，让它从写测试开始，而不是从头再探一遍。

任务队列不能只活在对话里

队列以前只存在主代理的会话记录里。会话一旦被压缩、或者换一个 agent 接手，队列就没了——而 worktree 和分支还在，没人知道还剩几个任务没做。现在一份在会话里当读写入口，一份落在仓库的 .git 目录里（pipeline/queue.md）当恢复入口，两处对不上以磁盘那份为准。这是把「计算和状态分开」的思路搬进自己的流程：会话是随时可丢的计算，队列是必须留下的状态。

派发材料要分层写

主代理交代给执行者的材料，不是越多越好，也不是越少越好。分三层：执行者不拿到就得自己重新发现的事实（数据位置、函数名、示例行号），主代理要直接写进材料里，别指望它自己去翻；它能自己读的给路径指针；只在需要时才看的给入口。漏了第一层的，它会自己发明一套方法去探——这就是上下文被探索吃光的原因。

大仓库检出 worktree 必须放后台跑

十几万文件的素材仓，跑 git worktree add 一次检出的耗时一定超过命令工具的前台超时——必被杀，留下一个半截的检出结果：文件数只有一半、index.lock 残留，但 git status 偏偏报「0 个缺失」——这个假象最坑人，会让你以为检出结果是完整的。判断办法是三个特征一起看：文件数远少于预期、status 报 0 缺失、关键路径不存在。三条同时成立就说明这棵树救不回来，清掉重建，别在半截上补跑。

从 DeepSeek 的 Super-agent 借了什么

前两天看到 DeepSeek Harness 团队发的《Super-agent 设计探索：迈向更自主的 Agent 系统》（GitHub），对照之下我吸了四点：

  1. 主代理把任务队列从一份改成两份——对应它的「计算与状态分离」：一份留在会话里当读写入口，一份落在仓库 .git 目录里（pipeline/queue.md）当恢复入口，会话被压缩或换 agent 接手时状态还能找回。
  2. 主代理派发时写下两条判断标准和一个时限——对应它的 Watchdog：不再干等回报，主代理只看 git log 的提交数和 progress.md 的修改时间这两个确定性信号；超了时限先判断执行者是不是卡住，不是继续等。
  3. 主代理把派发材料分三层写——对应它的 Inline & Spill：执行者不拿到就得自己重新发现的事实直接写进材料，它能自己读的给路径指针，只在需要时才看的给入口；漏了第一层，它会自己发明一套方法去探。
  4. 主代理向在跑的执行者追加输入——对应它的订阅直通：同一份描述下的裁决直接送回在跑的执行者，不换来一次完整的重派和还原（宿主支持时）。

但也有刻意没搬的：投机执行（我的原则是子代理只在我明确派了活之后才动手，不能在我还不确定时就在后台预做）；Router 批处理（DeepSeek 的 Router 能攒批，是因为它处理的是中立的环境事件流；我这里的「回报」是子代理各自承载判断责任交回来的结论，必须逐一核对，不是能让你攒批的原始输入）；Session 对用户隐藏（我的四个文件恰恰是把会话结构显式化给审查者看的审计面，隐藏它等于拆掉制衡）。

那篇文章的核心判断——「单任务上限取决于模型能力，多任务上限取决于人的注意力，一个人通常只能同时跟进 3 到 5 个活跃 Session」——和我的「在跑任务不超过三个」是同一个观察的另一种量化。有外部依据了。

这东西不适合谁

契约开头就写了硬前提：宿主必须能派发具备独立上下文的子代理，并且能读写项目文件、运行命令、用 Git worktree。 做不到这些，这个技能不适用——它没有降级模式，同一个上下文既实现又审查是不允许的。

它的开销不随改动缩小：小到 agent 几分钟能写完、自己一眼能验完的活，用它的成本大于收益；全量测试跑十几分钟、又没有更快分层办法的项目，也要重新掂量。
